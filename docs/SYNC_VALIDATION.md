# Sync validation — method, extent, and limits

Beyond All Reason is lockstep-deterministic: every client simulates the whole
game and only player *commands* cross the network. That only works if every
machine computes **bit-identical** floating-point results for every one of
millions of operations per game. A port that gets one bit wrong anywhere in
the simulation desyncs — worst case mid-game, for every player in the match.

We assumed this port would break sync, and set out to prove that it did.
This document describes exactly what was tested, how you can reproduce it,
and what remains unproven. Every claim states its evidence, and every set of
numbers states the engine version and build it was measured on: sections 1 to 4
come from the original port at engine 2025.06.24 unless a subsection says
otherwise, and 3a and 3b are this repository's own runs. Evidence from one
engine version does not certify another (section 5).

## How sync is measured (for non-engine-devs)

The engine computes a checksum of the synced simulation state every frame
(`SyncChecker`). Recorded games (demos, `.sdfz`) embed the checksums the
recording client computed. Re-simulating a demo (`spring-headless` replays
the command stream through the full simulation) recomputes every frame's
checksum and compares against the recorded ones: one bit of divergence in
any unit position, projectile, RNG draw, or economy value fails the run with
a sync error. A full-length 8v8 demo is therefore a test with tens of
thousands of consecutive per-frame assertions over the entire sim codebase.

## 1. Floating-point foundation: streflop bit-exactness

The engine's synced math runs on streflop (ARM64/NEON support merged
upstream in PR #2819). The cross-architecture test suite exercises 52,080
operations (all libm entry points over denormals, near-branch-cut values,
huge/tiny args) and compares bit patterns:

- AppleClang arm64 NEON build vs the committed arm64-NEON reference:
  **52,080 / 52,080 bit-exact**.
- vs the committed x86_64-SSE reference: **47,852 / 47,852 bit-exact**
  (result-set hash `EA2881A4F127BF10`).
- Same binary run natively (arm64) vs under Rosetta 2 (x86_64-SSE):
  **52,080 / 52,080 bit-exact**.

Reproduce: build `tools/sync-test` (in this tree) and run it against the
committed references under `tools/sync-test/reference/`
(`scripts/run-synctest.sh`, which also requires at least 40,000 tests in
common with each reference).

This suite builds its own streflop and covers the single-precision functions.
It says nothing about the double-precision libm, which section 2 covers. The
single-precision functions are the only streflop libm functions the engine
links, on macOS and on the x86 Linux build of the same tree
(`scripts/check-dbl64-marker.sh`).

## 2. Fleet libm parity: the hybrid streflop build

Linux/Windows release builds are compiled with gcc, which passes
`-fsingle-precision-constant` — a gcc-only flag that demotes unsuffixed FP
literals in streflop's double-precision libm to float precision. Clang has
no equivalent, so a pure-clang build diverges from the fleet by up to ~45
ULPs in `asin`/`acos`-family results. The build therefore recompiles the
dbl-64 objects with gcc, swaps them into the streflop archive and verifies
the result: a hash harness (`scripts/dfp-small.cpp`, 21 lines over every
double function the library can link, each over a large deterministic input
sweep) must reproduce the hashes of a gcc x86-64 Linux build line for line.
The reference is generated by `scripts/gen-libm-ref.sh` in upstream's own
build image. This check is a mandatory step of every build; a build that
fails it does not ship.

What this does and does not show:

- It tests the archive. The engine binaries are checked separately
  (`scripts/check-dbl64-marker.sh`, in the build and again on the staged
  release binary): a double libm function linked into one must come from the
  gcc-built objects.
- On 2026.09.02 no engine binary links a double libm function at all. The
  engine calls the single-precision functions only, and the same is true of
  the x86 Linux build of this tree. The swap is therefore a guard for the day
  engine code starts calling one, not something play depends on today.
- Two double functions are wrong on every platform, the fleet included:
  `expm1(x)` and `cosh(x)` return NaN for `|x|` below 2^-54, because
  `-fsingle-precision-constant` turns the library's `huge = 1.0e+300` into a
  float infinity. The NaN carries the platform's sign bit (set on x86, clear
  on arm64), so the harness hashes every NaN as one pattern. Nothing in the
  engine calls either function on doubles.

## 3. Full-game replay certification vs official recordings

Demos recorded by **official builds** (public releases played by the live
community) re-simulated on this port, every frame checksum-compared:

| Demo | Frames | Result |
|---|---|---|
| Public replay matrix (6 demos, mixed maps/modes) | — | 6/6 PASSED |
| Iron Isle 8v8 (48 min) | 86,632 | PASSED, zero sync errors |
| Rosetta 8v8 (53 min) | 87,936 | PASSED, zero sync errors |
| All That Glitters 8v8 | 92,040 | PASSED, zero sync errors |
| Final certification: public-release 8v8 | 66,589 | REPLAY_SYNC_OK, zero sync errors |

Reproduce: `scripts/replay-check.sh <demo.sdfz>` with the matching game and
map content present. It prints `REPLAY_SYNC_OK` when the replay reaches its end
with no `[DESYNC WARNING]` line, and refuses a demo recorded on another engine
version. The replay must have been recorded on the engine version being tested
(`scripts/find-fleet-replays.py <version>` lists public ones).

## 4. Live cross-platform multiplayer (the real thing)

Replays prove the sim; live games additionally prove the network path, and
the server compares checksums across *different* machines in real time.

**Phase B3 — vs the official Linux release binary** (unmodified release
download, x86-64, running in a VM): both hosting directions, smoke games,
full 1v1s to natural game end (f≈38,753 and f=18,172), and a 16-player

## 5. Honest limitations

- **Replays exercise recorded content only.** Code paths no recorded game
  hits are not covered by §3. The live matrix (§4) and PvE modes broaden
  this, but coverage is necessarily of what was played.
- **Every engine or game-version bump requires re-validation.** These
  results certify this exact engine tree and driver stack. The gate suite
  (streflop sync-test, libm hashes, replay re-simulation) reruns per
  release, and any compiler or flag change triggers the full-length replay
  certification again.
- **Compiler risk is managed, not eliminated.** The fleet ships gcc; this
  port ships AppleClang plus the gcc object swap (§2). Outside streflop,
  identical results rely on IEEE-754 semantics with `-ffp-contract=off`
  globally and no fast-math anywhere in synced code (the Metal shader
  fast-math option affects only unsynced rendering — shaders never feed the
  simulation).
- **Marathon headless re-simulations can end early on the game's Lua memory
  ceiling, not on sync.** The engine's Lua allocator budget (a game modrule,
  1.5 GB) is counted globally across synced and unsynced Lua; a flat-out
  re-simulation of a very long 8v8 with the full UI widget set loaded can
  brush that ceiling and exit — with every frame up to that point still
  checksum-verified, and at a different frame on each run (allocator/GC
  noise, not simulation state). Observed on this port only within ~1% of the
  end of the longest (92k-frame) demo; the same class of Lua memory pressure
  is visible on official binaries in long headless runs. Live games are
  unaffected (our longest live soak game ran 100,657 frames).
- **Desync triage is built in.** During demo playback,
  `SPRING_DUMP_STATE_RANGE=min:max` dumps full synced state (RNG, units, features, projectiles, raw floats) per
  frame in the range, so any reported desync can be bisected to the exact
  frame and subsystem against a reference dump.

## Appendix A — register of synced-code changes

This is every change the macOS layer makes to code that can reach synced
state, relative to the upstream release tag it is based on. It is read off the
diff, not kept by memory. Regenerate it at every engine bump, and whenever one
of these paths changes:

    git diff --stat <upstream tag> HEAD -- rts/Sim rts/lib/streflop \
        'rts/Lua/LuaSynced*.cpp' rts/System/Sync rts/System/FastMath.h \
        rts/Net/GameServer.cpp

Measured against `2026.09.02` at commit `5ae54cd976`. `rts/lib/streflop` is
unchanged: it is the same submodule commit as the tag.

| Change | Files | Applies to | Why the fleet's x86 results are unchanged |
|---|---|---|---|
| COB `SHIELD_POWER` has a defined result outside `int` range | `rts/Sim/Units/Scripts/UnitScript.cpp` | every platform | In range it is the same conversion. Out of range, or for NaN, x86 already produces `INT_MIN` (`cvttss2si`); the change returns that value explicitly. On arm64 it replaces a saturated `INT_MAX`, which was a real divergence from the fleet (upstream issue #3421). |
| Heading casts go through `int` | `rts/Sim/MoveTypes/HoverAirMoveType.cpp`, `rts/Sim/Path/IPathController.cpp`, `rts/Lua/LuaSyncedMoveCtrl.cpp`, `rts/Lua/LuaSyncedRead.cpp` | every platform | Below 2^31 it is the same instruction and the same truncation on x86, and arm64 now gives the same value. Known limit: from 2^31 upward x86 gives 0 and arm64 gives -1. Game Lua would have to pass such a heading on purpose. |
| QTPFS shuts down only the systems that were created | `rts/Sim/Path/QTPFS/PathManager.cpp` | every platform | Destructor only, and both systems exist before the first frame of any game (upstream PR #3694, open). |
| FPU control check on NEON | `rts/System/Sync/FPUCheck.cpp` | arm64 only | Not compiled on x86. On arm64 it re-applies streflop's own settings when the rounding mode or the flush-to-zero bit has drifted (upstream PR #3689, open). |
| `SPRING_DEMO_SPEED` | `rts/Net/GameServer.cpp` | every platform, demo playback only | Changes playback pacing, not simulated state. Sync is checked the same way at any speed. |
| `math::sqrtf` declaration | `rts/System/FastMath.h` | translation units built without streflop | No synced translation unit sees it: the condition mirrors the one in `streflop_cond.h`. |

Build-level controls. These are not source changes, but the port's sync
rests on them:

| Control | Where | What checks it |
|---|---|---|
| The dbl-64 libm objects are compiled with gcc 15, as the fleet's are, and swapped into the streflop archive | `scripts/gcc-dbl64-swap.sh` | the libm parity gate in `scripts/build-engine.sh` (21 hash lines over every double function that links, against `testkit/libm-refs/`) and `scripts/check-dbl64-marker.sh` on the binaries |
| `-ffp-contract=off` and no fast-math in synced code | upstream's CMake | the streflop sync test and the replays |
| The macOS build reports the release version | `rts/build/cmake/ConfigureVersion.cmake` | `scripts/replay-check.sh` refuses a version mismatch |

Now upstream, and no longer part of the layer (earlier versions of this
register listed them): the COB float-to-short casts (#3075), the
`GroundMoveType` heading cast (#3342) and `views::enumerate` compatibility
(#3289). Dropped because upstream declined it: the destructor null guards for a failed save-game load (#3280; upstream's own answer, #3277, is in the tag). The original port's glibc dbl-64 import and its `math::floor`
emulation belonged to the 2025.06.24 lane and are not in this tree: here
`math::floor(float)` is streflop's software floor on every architecture.

Sections 3a and 3b are the evidence for this table. A row changed after the
date of a replay is not covered by that replay.
